# 01 项目定位与交付结论

应急先行是一套在 Orange Pi 6 Plus 上运行的离线应急辅助原型。系统针对“网络不可用时如何获得本地视觉提示和处置资料”以及“没有人工持续上传图片时如何监测视频”两个问题，提供图片问答、定时视频采样、人员与烟火检测、事件提醒和证据报告。

本文对应 2026 年 11 月 24 日归档的**原版 8080 项目**。原始目录为 emergency-agent，GitHub 整理副本为 emergency-agent-github。另一个 emergency-agent-npu / 8081 项目是独立实验，未并入本次原版代码。本次没有修改原版配置、权重、历史对话和报告。

| 能力 | 当前事实 | 验证边界 |
|---|---|---|
| 本地语言模型 | Qwen2.5-3B Q4_K_M，经 llama.cpp 在 CPU 上运行 | 已保存历史吞吐记录；本次完成真实生成冒烟测试 |
| 人员 / 烟火检测 | 两个 DAMO-YOLO 模型，经 PyTorch 在 CPU 上运行 | 已做样例验证与单图重复性能测试 |
| 持续监测 | 本地视频、定时抽帧、常驻检测、事件合并 | 已有照片序列与游客视频验证记录 |
| NPU 人员候选 | 可选 CIX YOLOv8s 适配器，未自动启用 | 历史结果 needs_review；存在计数差异 |
| NPU 烟火与 DAMO 迁移 | 位于独立实验分支 / 项目 | 不能作为原版已实现能力 |
| 工程交付 | 独立源码、依赖、配置生成、部署和验证脚本、PDF 源稿 | 新目录离线复用部署通过；全新联网安装未实测 |

核心结论：原版已经具备“输入—检测—提示—留痕—复核”的本地流程，但烟火泛化能力存在明确不足。当前证据支持功能原型展示和后续开发，不支持宣称已达到专业消防报警设备的检出率、稳定性或认证要求。

本文把软件测试、部署连通性、单图速度、完整任务时延、模型精度分别讨论。不能把模型可加载理解为精度达标，也不能把 NPU 前向耗时理解为用户等待时间。

数据分为两类：B01–B07 是原机保存的历史测量，导出时仅移除本机目录标识或提取必要统计；B08 是本次在整理副本上重新执行的 CPU 测量。原始来源哈希和变换方式见 benchmarks/provenance.json。没有用模拟结果填补缺失的硬件数据。

# 02 场景、功能与验收口径

图片问答场景：用户上传图片并问“有几个人”“有没有烟火”“应该如何处理”。系统先判断问题所需能力，按需要调用检测或知识检索，随后生成回答并保存证据。一般知识问答不会因为附带图片而强制统计人数；不支持的衣着、伤势等图像问题会说明能力边界。

持续监测场景：用户选择本地视频并启动采样。系统持续检查新的播放位置，无需每次上传照片和重新提问。默认烟火检测，可选人员提醒；人员出现只是场景提示，系统不能由“有人”推断“有人被困”。

| 验收层次 | 观察内容 | 不能替代的验证 |
|---|---|---|
| 软件单元 / 前端逻辑测试 | 路由、坐标恢复、阈值、取消、故障、状态转换、同源限制 | 真实模型精度和板端 NPU 驱动 |
| 部署冒烟测试 | 指定文件、运行时和模型能生成真实输出 | 数据集精度、长期稳定性 |
| 图像性能测试 | 指定图片、模型、线程下的可复查计时 | 多路视频、并发问答与实时性承诺 |
| 监测流程测试 | 抽帧、事件合并、持续提醒、截图、结束状态 | 真实火灾早期发现率 |
| 精度验收 | 带完整标注的数据集上的 precision、recall、mAP、事件误报漏报 | 当前尚未完成 |

本项目目前没有摄像头输入。照片硬切视频用于验证事件先后关系；真实游客视频用于人员场景和烟火负例。这两类素材都不能代替真实烟火视频的泛化评价。演示时应同时展示一次漏检或未知状态，说明系统如何保留人工复核入口。

持续监测的报警链目前止于网页、事件记录和浏览器声音。没有 GPIO 蜂鸣器、短信、电话或消防平台联动。浏览器声音受用户手势策略控制，未点击启用声音或关闭页面时不能承诺发声。

建议演示验收依次检查：部署检查输出实际后端；导入本地视频；观察人员/烟火出现与重复事件；切换空场观察事件结束；查看截图和模型哈希；提交一条带图问题；最后展示原始性能记录和已知限制。

# 03 系统架构与模块职责

系统采用本地 HTTP 服务、工具进程和文件证据存储的结构。前端 HTML/CSS/JavaScript 直接从本机加载，无外部字体或 CDN。HTTP 与 SQLite 由 Python 标准库提供；视觉依赖隔离在明确指定的 Python 环境中；语言模型由 llama.cpp 子进程执行。

<!-- architecture -->

| 模块 | 文件 | 职责 |
|---|---|---|
| 任务入口 | webapp.py、agent.py | 输入验证、异步任务、会话上下文、CLI 与报告 |
| Agent 决策 | agent_loop.py | 本地模型选择工具、控制轮次、复用证据、校验答案 |
| 视觉适配 | tools/detect_person.py、detect_fire_smoke.py | 模型哈希、离线加载、预处理、检测、输出校验 |
| 风险规则 | triage.py | 证据、阈值、不完整能力与“未知”状态 |
| 连续监测 | monitor.py、tools/monitor_video.py | 视频导入、采样、进程生命周期、事件合并 |
| 知识与证据 | knowledge/、data/ | 本地资料、SQLite、图片、报告与人工确认 |

图片问答与监测共享检测适配器，但生命周期不同。问答可以按任务启动工具进程；监测使用持久化检测进程，避免每帧重复加载模型。监测不逐帧调用 Qwen，只有用户提出问题时进入语言模型任务链，因此语言模型较长的生成时间不直接阻塞定时视觉采样。

桌面壳保留为可选入口，复用同一个网页后端；本次主要交付仍以网页为准。后端、报告和模型调用的行为不会因桌面窗口而自动改变。

# 04 模型清单、来源与部署方式

| 模型 | 部署形态 | 运行设备 | 原始文件大小 |
|---|---|---|---|
| Qwen2.5-3B-Instruct | 本地转换的 Q4_K_M GGUF | CPU / llama.cpp | 1,929,902,432 bytes |
| DAMO-YOLO 人员 | .pt + 本地架构和标签文件 | CPU / PyTorch | 130,945,473 bytes（权重） |
| DAMO-YOLO 烟火 | .pt + 本地架构和标签文件 | CPU / PyTorch | 131,084,119 bytes（权重） |
| 可选 YOLOv8s | CIX 已编译 .cix | CIX NPU / NOE | 13,424,980 bytes |
| 兼容保留 SSD300 | CIX 已编译 .cix | CIX NPU / NOE | 23,738,396 bytes |

Qwen 使用官方 Qwen2.5-3B-Instruct 源权重，经本地转换和 llama-quantize 得到 Q4_K_M。现用 GGUF 的 SHA256 是 e81b15458f70331bd27be72c8b18ec9e39d4fcd68d821642588616d1c796d897。benchmark 中 model_size=1,923,946,496 表示张量载荷大小，不能替代文件实际字节数。

语言模型运行时固定为 llama.cpp 提交 d88040c704c8855c497d46c20675a3d492f70f94，CPU 构建。生产任务使用最多 8 线程、上下文 4096、最大输出 384，原机优先亲和性为 0,1,6-11。配置生成器会与当前机器允许的 CPU 集合取交集，避免在限制性环境或不同核心数机器上指定无效 CPU。

DAMO-YOLO 人员模型来源 iic/cv_tinynas_human-detection_damoyolo，烟火来源 iic/cv_tinynas_object-detection_damoyolo_smokefire。模型目录中的权重、damoyolo.py、标签和结构文件必须与 source.json 中的 SHA256 一致。代码显式加载本地 DamoYolo，并核对类别数和标签映射，不依赖可能陈旧的通用 pipeline 配置。

加载路径使用 device='cpu'，设置 PyTorch 线程数，推理期间禁止网络连接并启用离线环境变量。torch 权重采用 weights_only 路径；本地模型架构代码仍属于受信任输入，因此文件校验和来源留存不能省略。

部署目录中的 config.json 是本机生成文件，不进入 Git。config.example.json 提供可移植模板，scripts/configure.py 把模型、解释器和验证文件转换为当前目录的绝对路径。每次迁移路径后重新生成配置，并重新执行样例验证。

# 05 视觉预处理与输出契约

两个 CPU 模型遵循上游 DAMO 输入约定：RGB，数值范围 0–255，CHW 浮点张量。最长边缩至不超过 640，小图不放大，按 stride 32 在右侧和底部补零。检测框按两个方向的实际缩放比例还原到原图，并裁剪到图像边界。

这与常见 YOLO 的 BGR、除以 255 或居中 letterbox 处理不能随意互换。移植时即使输入形状相同，颜色、范围、缩放和 padding 的差异也可能造成系统性漏检。软件测试检查纯色图的像素范围、补边区域和坐标恢复。

| 输出字段 | 约定 | 异常处理 |
|---|---|---|
| detections | 列表；每项含 label、confidence、box | 缺字段或结构不一致视为失败 |
| label | 人员模型仅 person；烟火仅 smoke/fire | 未知类别拒绝，不改名后继续 |
| confidence | 有限数值，范围 0–1 | NaN、无穷或越界拒绝 |
| box | 原图像素坐标 x1,y1,x2,y2 | 裁剪边界，拒绝无效面积 |
| image_size | 原图宽、高，均为正数 | 无效尺寸拒绝 |
| device / source | 实际调用设备和适配器来源 | 写入报告，不用文件后缀推断设备 |
| model_sha256 | 现用权重标识 | 与清单和样例记录核对 |

人员默认检测阈值为 0.50；烟火检测阈值为 0.60。风险评估还存在 fire_threshold=0.75、smoke_threshold=0.70 等规则门槛，它们与检测器筛选阈值是不同层次。视频事件使用检测器已筛选输出，不应假定它与静态报告的风险等级完全等价。

标记 ready 前必须检查实际模型、环境和样例。验证 marker 绑定配置与文件指纹，不能把旧目录中的 passed 文件复制到新路径冒充已验证。本次部署脚本在新目录生成新的 marker，历史测量保存在 benchmarks/historical，不写入活动 data 充当新测试。

空列表只表示本次成功运行后未超过阈值的目标；模型失败、未覆盖某类别、图片无效或工具未调用时，结果保持未知。系统不会把“工具返回异常”转换成“无人无火”。

# 06 异构算力调用与启用门槛

原版具有 CPU / NPU 的配置分发结构，当前默认活动链全部在 CPU。没有 GPU 推理和 GPU 基准。硬件具备 NPU、模型扩展名为 .cix 或发现 /dev/aipu，均不足以证明一次任务实际经过 NPU。

| 任务 | 当前默认后端 | 可选后端 | 分发条件 |
|---|---|---|---|
| 文本规划 / 回答 | llama.cpp CPU | 本仓库无已验证 NPU 文本后端 | 读取 model_path、llama_cli |
| 人员检测 | DAMO-YOLO CPU | CIX YOLOv8s；兼容 SSD | 读取 person_detection.backend |
| 烟火检测 | DAMO-YOLO CPU | 原版无已启用 CIX 烟火后端 | fire_smoke 配置与有效 marker |
| 图像预后处理 | CPU | 部分 CIX 模型前向可交给 NPU | 图像解码、resize、NMS 仍有 CPU 成本 |
| 视频解码 / 事件 | FFmpeg 与 Python CPU | 未测视频硬件解码路径 | 不宣称 GPU/VPU 加速 |

历史函数名 run_npu_detector 实际承担人员后端分发；当 backend=damoyolo 时它调用的是 CPU。审计应看配置、source、device、模型哈希与硬件实测记录，不能仅依据函数名命名。

NPU 人员适配器通过 NOE runtime 加载 CIX，YOLOv8s 输入为固定 640×640，输出含 COCO 类别。本项目只保留 person 类，不能借该模型宣称具备 smoke/fire。图像处理和解码/NMS 仍在 CPU 上。

切换前需满足：真实设备节点存在、驱动和 NOE SDK 匹配、编译目标匹配、输入输出与量化参数核对、逐样例结果稳定、人工参考完整。compare_person_npu.py 会保留对比报告；通过后才允许 --activate 修改人员后端，并备份原配置。未通过则继续保留 CPU。

2026-11-24 的原机对比状态是 needs_review、activated=false。六人照片 NPU 只检出四人；另一个样例原参考只点了四名前景人，背景小人未完整标注。这同时说明模型差异和参考标注不足，不能只靠“检出数等于旧数字”定义精度。

本次整理环境未透传 /dev/aipu，未重新执行硬件测试。下文 NPU 数据引用原机保存记录；本次新测量仅涉及 CPU。

# 07 Agent 决策、知识检索与证据约束

Agent 使用本地 Qwen 生成受限结构化决策，允许选择人员检测、烟火检测、本地知识检索和评估工具。最多三轮工具规划，之后整理最终回答。它具有基于上下文选择工具的能力，但不是无约束的自我思考系统；可用工具、轮次、输出格式和证据校验由代码限制。

| 阶段 | 输入 | 处理及留痕 |
|---|---|---|
| 问题识别 | 用户文本、是否有图、历史对话 | 判断所需能力，避免所有问题都走人数统计 |
| 工具选择 | 当前证据、工具菜单、剩余轮次 | 模型输出工具决策；解析失败进入恢复路径 |
| 执行 | 本地图像、检索 query、配置 | 子进程运行、超时处理、结构校验、来源记录 |
| 证据复用 | 图片哈希、模型和配置指纹 | 仅同图、同配置、成功工具结果可复用 |
| 回答校验 | 统计、风险、能力缺失、模型草稿 | 人数和火情等不能背离检测证据；必要时规则兜底 |
| 结果保存 | 最终答复、工具轨迹、图片、确认 | JSON/HTML/Markdown 与证据图片、模型哈希 |

会话上下文引用服务端已保存报告，客户端不能直接提交任意“检测记忆”冒充真实结果。缓存键包括图片哈希及工具相关配置与模型指纹；更换图片、模型或阈值后，旧成功结果不能直接沿用。失败结果不作为“无目标”缓存。

SQLite 知识检索采用本地资料与文本匹配，不是向量数据库或经过验证的官方知识图谱。knowledge/*.md 为项目整理提示，标注 project_curated、pending_local_review；需要专业人员审核来源与表述后才能扩大使用范围。生成模型不能为不存在的来源补造引用。

任务系统保存 queued、running、completed/failed/cancelled 等状态，支持取消与错误回传。前端输入控制可在完成、失败、超时或取消后恢复，避免一直显示“处理中”而无法继续提问。服务退出时显式终止所属任务进程组，重启后把中断任务标为失败。

历史完整 Agent 示例的时延在数十秒级，主要包含多次语言模型规划/生成以及工具调用；持续监测不依赖这一循环。不能用 16 token/s 推断一次完整提问仅耗一两秒。

# 08 持续监测、事件状态与时延模型

视频由 FFprobe 检查时长、分辨率与视频流；上传限制为 200 MiB，最长边不超过 8192。FFmpeg 只允许本地 file/pipe 协议和受限容器格式。导入的视频保存在当前副本的 data/monitor/videos，不通过接口接受任意本机路径。

监测进程按墙钟选择播放位置，抽取最新需要的画面。烟火与可选人员模型各有常驻进程，先向全部检测器发送帧，再读取结果，使两类检测可以重叠执行。监测中没有无限帧队列；处理变慢时跳过已过时的位置，而不是把延迟不断积累。

| 状态条件 | 事件动作 | 语义 |
|---|---|---|
| 首次检出某类 | 创建事件、first_seen、网页提醒 | 立刻提示，不等待第二次 |
| 连续两次检出 | persistent；持续 fire 升级 critical | 重复证据增强，不等于确认火灾 |
| 持续出现 | 同类别事件更新计数与置信度 | 类别级合并，不是个体跟踪 |
| 连续三次未检出 | ended，保存结束原因 | “暂未再次检出”，不表示现场安全 |
| 视频结束 / 用户停止 / 故障 | 保存状态并结束活动事件 | 后续画面未检测，不能推断风险解除 |

设采样间隔为 Δ，抽帧耗时为 Tcap，两个检测器耗时分别为 Tp、Tf，状态写入耗时为 Tw。理想并行时单次周期约为 Tcap + max(Tp,Tf) + Tw；CPU 争用可能使并行检测器各自变慢，因此不能简单把两个独立单模型均值当作并发视频结果。

当周期小于 Δ，目标随机出现到首次处理完成的延迟约为 0 到 Δ 加一个处理周期；若目标只在两次采样之间短暂出现，则可能完全漏采。若周期超过 Δ，实际采样密度会下降。第二次连续确认还需要新的样本时间，故“2 秒抽帧”不是“所有火情 2 秒内必报警”的保证。

普通帧仅保留近期少量文件；事件截图保留用于复核。事件、报告和上传素材仍会增长，当前没有生产级容量上限和长期归档策略。长期部署需加入磁盘阈值、保留期限、健康检查和自动恢复策略。

# 09 真实性能数据与计时口径

# 10 优化经验与失败复盘

第一项优化是常驻模型。冷加载约 3.2 秒，而本次热 infer 约 0.24–0.25 秒。在持续监测中把检测器留在进程内，避免每帧重复初始化，是当前可由实测支持的优化方向。两种计时范围不同，不把二者比例直接称作端到端加速倍数。

第二项是解耦视觉与语言模型。视频循环只做采样、视觉和事件规则；Qwen 用于用户问题和整理回答。这样不会每个采样周期重复支付数十秒的 Agent 开销。用户想看实时状态时，先显示明确视觉证据，再根据需要提问。

第三项是控制输入和线程。最长边 640、stride 32、8 线程和 CPU 亲和性限制了算量和资源波动。但两个 8 线程检测器并发时可能竞争相同核心，不能保证线性加速。后续应在固定视频上对 2/4/6/8 线程组合测周期 p95，再选择配置。

第四项是只复用可信证据。图片哈希、模型版本与配置指纹一致时复用成功工具结果，减少同图追问的重复检测。模型或阈值变化后缓存失效，避免“看起来更快”却沿用过期结论。

第五项是保留未知和失败。没有能力、工具异常、输出无效和空检测必须区分。风险规则与模型草稿相矛盾时，优先保留可验证事实；任务可取消、超时可回收，防止界面长期卡住。

## CIX 迁移中发现的量化问题（独立实验经验）

另一个 NPU 实验曾把边框坐标与类别概率合并为一个 INT8 输出。坐标可达数百像素，而概率只在 0–1。若共用一个量化尺度，概率分辨率可能被坐标动态范围淹没，出现“模型成功运行但所有类别分数为零”的现象。

该独立实验中记录的反量化形式为 real≈(q−zero_point)/scale，人员与烟火合并输出的 scale 约为 0.245596、0.282083，对应最小步长约为 4.07、3.55。0–1 概率无法有效表示；浮点可检出三人的图片在该量化形式下可能变成空检测。这是特定导出和量化方案的问题，不能推广为所有 CIX 模型都有此缺陷。

改进方向是把 boxes 与 scores 拆为独立输出，分别校准量化范围；核对类别编号、输出维度和 NOE 实际 scale/zero point，再在浮点、量化仿真、编译后板端三级逐图对比。新图导出或 CPU 对齐通过，不等于 CIX 编译和板端精度已经通过。

该修复经验只作为后续迁移设计参考。原版仓库保留的是原有候选导出工具，没有把独立实验代码合并或将其写成原版已完成 NPU 烟火能力。SDK/CixBuilder 版本、编译目标、校准集和真实板端日志需随未来版本一并归档。

# 11 可复现部署与资源管理

交付分为公开代码、独立模型包、本地样例包。公开仓库不带虚拟环境、历史对话、数据库、上传照片和模型大文件。models_manifest.json 与 samples_manifest.json 列出相对路径、字节数、SHA256；文件名相同而哈希不同不能冒充同一版本。

新机器先准备 Debian 12 / Python 3.11、编译工具、FFmpeg 和 taskset，再运行 deploy.sh。脚本验证资源后安装 Python 依赖，固定提交构建 CPU llama.cpp，生成本机配置，验证模型和 LLM，初始化知识库，最后启动网页。没有校验到资源或任一步失败时明确退出。

```bash
./deploy.sh \
  --models /path/emergency-agent-models-20261124.tar.gz \
  --samples /path/emergency-agent-local-samples-20261124.tar.gz \
  --host 0.0.0.0 --port 8082
```

原机可增加 --runtime-python 和 --llama-cli，复用已有运行时，避免联网下载。本次真实验证采用该离线路径；模型与样例复制到整理副本，重新生成 marker，并完成真实生成。验证流程共约 27.5 秒，不含整个归档解压、哈希与依赖安装，因此不能作为“一键部署总耗时”。

完全离线的新机器需要 ARM64/Python 3.11 的完整 wheel 目录，以及目标系统上的 llama.cpp 构建及共享库；不是只复制脚本或 x86 二进制就能运行。全新联网安装与第三方源可达性本次未实测。

原机原版仍用 8080；整理副本演示建议 8082，避免占用 8081 实验项目。后续只需 start-web.sh 启动，不必重复安装。浏览器从另一台电脑访问时使用同一局域网、--host 0.0.0.0 和板卡实际 IP。

所有运行数据写入当前项目 data/；配置也是当前项目自己的 config.json。复用的旧解释器与 llama.cpp 是外部运行依赖，部署脚本不向其安装新包或改写原项目。迁移机器后必须重新生成路径，不能把原机绝对路径当作通用部署方案。

# 12 验证结果、故障处理与运维边界

本次在无模型和历史数据的干净代码副本上执行软件验证，117 项 Python 测试与 6 组前端逻辑测试全部通过。测试覆盖资源包校验与路径限制、路由、坐标、风险未知状态、Agent 证据约束、缓存失效、任务取消、报告留存、监测事件、同源限制和 NPU 启用门槛。模拟激活测试不是硬件 NPU 测量。

在有资源的整理副本上完成 CPU 人员（三人和空白）、烟火样例、本地 Qwen 生成验证。另完成一次真实 Agent 图片问答：三人照片检出 3 人，回答“这张图显示有3个人。”，耗时 31.154 秒，状态 completed；这是单次功能验收，不是稳定性能均值。新性能记录按模型独立进程产生，保留 5 次热调用原值。HTTP/API 测试在内存中运行；当前受限执行环境不能监听服务端口，本次不把浏览器实际联机展示写成已完成验证。

| 现象 | 检查顺序 | 恢复动作 |
|---|---|---|
| 页面打不开 | 端口、进程、监听地址、板卡 IP | 在本机终端启动；原服务占用时换 8082 |
| 模型显示未就绪 | 路径、SHA256、Python 依赖、marker | 用配置的解释器重新 validate_models.py |
| 明明有人却为空 | 后端、类别、预处理、阈值、原始分数 | 保留图片和日志，对照 CPU，不直接宣布无人 |
| 任务长期处理中 | 子进程、任务状态、超时/取消 | 取消并检查日志；保留错误，不无限重试 |
| NPU 不可用 | /dev/aipu、SDK、编译目标、权限 | 未通过验证时保留 CPU，不伪报加速 |
| 有事件但没声音 | 用户手势、页面是否打开、浏览器策略 | 点击启用声音；用事件列表核实检测是否发生 |

安全与使用范围：HTTP 服务有同源、路径和输入大小限制，但没有完整账号和权限系统；默认只监听本机，局域网演示应在受信任网络。历史图片和对话不进入 Git。生产上线还需要访问控制、加密传输、审计策略和备份恢复。

长期可用性仍需补充：摄像头接入、设备断连恢复、进程守护、磁盘与温度监控、重启后的明确状态、告警送达确认、长期压测和版本回滚。当前测试通过只证明测试覆盖范围内的行为，不等于这些运维能力已经具备。

# 13 后续研发计划与验收指标

优先级应先解决检测可信度，再追求单次前向速度。对原版的最直接改进是构建合法、独立、带完整标注的测试集，覆盖明火、烟雾、背光、蒸汽、红色物体、夜间、小目标、遮挡和空场。训练/校准/测试必须按场景或视频划分，避免同源近邻帧泄漏。

| 优先级 | 工作 | 建议验收方式 |
|---|---|---|
| P0 | 烟火漏检分析与测试集 | 逐图 TP/FP/FN、precision/recall、mAP；单独报告小目标和夜间 |
| P0 | 视频事件级评价 | 每段起止时间、事件级漏报、误报次数/小时、首次提醒延迟 |
| P1 | CIX 双输出模型迁移 | 浮点→量化仿真→编译后板端逐层和逐图对照 |
| P1 | 端到端性能 | 固定视频、多次运行；加载、预处理、前向、解码、周期 p50/p95 |
| P1 | 并发与资源 | 监测+问答并行时的周期、取消响应、峰值内存、温度、功耗 |
| P2 | 摄像头与外设提醒 | 连续采集、断线重连、明确硬件报警与送达记录 |
| P2 | 长期运维 | 24–72 小时持续运行、磁盘策略、服务恢复与备份恢复演练 |

CPU 与 NPU 比较应固定同一批图片、同一预处理、同一阈值和尽可能一致的模型语义。模型本身不同（DAMO 对 YOLO）时，应同时列出检测效果与速度，不能把差异全归因于算力设备。

建议测量脚本保留：设备与运行时版本、模型哈希、输入哈希、采样策略、线程/亲和性、预热次数、每次样本、计时起止位置和失败数量。不能只导出一个最好数字；故障与空检测同样进入评价记录。

展示时可使用三组证据：正常识别展示流程；已知漏检展示边界；NPU 对比展示迁移方法与门槛。这比单纯宣称“离线、智能、实时”更容易复核，也能明确下一阶段的研发目标。
